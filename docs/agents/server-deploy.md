# gbrain: установка форка на новый Linux-сервер

Инструкция для агента, который ставит gbrain из форка `rustam-python/gbrain`
на чистый сервер. Здесь только то, что отличает форк от upstream и что уже
ломалось на реальном VPS. Общий порядок установки (init, импорт, скиллы)
описан в `INSTALL_FOR_AGENTS.md`. Читай его рядом и не дублируй.

Значения, которые у каждого сервера свои, записаны заглушками `<ВОТ_ТАК>`.
Агент берёт их у пользователя в шаге 1. Примеры даны только как образец формата.
Локальную установку на llama.cpp описывает `docs/agents/local-deploy.md`.
Этот документ про сервер с облачным провайдером моделей.

## 0. Правила для агента

* **Ничего не меняй, пока не пройден шаг 1.** Значения заглушек не угадывай и
  не бери из примеров.
* **Сначала проверяй, потом меняй.** Перед записью конфигурации покажи список
  «было → станет» и дождись согласия.
* **Не показывай секреты.** Строка подключения к базе, ключи провайдера и
  приватные SSH-ключи не попадают в чат, логи и файлы, которые ты создаёшь.
  В выводе заменяй их на `***`.
* Не создавай, не удаляй и не пересоздавай базы без отдельного согласия.
* Не ставь gbrain из npm (`npm i -g gbrain`, `bun add -g gbrain` без `github:`).
  Пакет `gbrain` в npm чужой.
* **Не запускай `gbrain self-upgrade`.** Он смотрит на upstream, а не на форк.
  Обновление форка идёт вручную (раздел 8).
* **PR только в форк** `rustam-python/gbrain`, никогда в `garrytan/gbrain`.
* После каждой записи читай значение обратно и сравнивай.
* Первые 2–3 раздела после установки проверяй на одном шаге, не пачкой.
  Остановись при первой ошибке и сообщи, не перебирай варианты.

## 2. Что в форке не так, как в upstream

Это всё, что нужно знать до установки. Подробности в `CONTEXT.md` и
`docs/adr/0001-*.md`, `0002-*.md`.

* **Слаги кириллицы сохраняют `й` и `ё`.** В upstream они складываются в `и` и
  `е`, и «Пётр» с «Петр» получаются одной страницей. В форке слаги разные, а
  слияние идёт в слое алиасов. Поэтому у форка своя версия грамматики слагов
  (`SLUG_GRAMMAR_VERSION`), и чекпоинт импорта, записанный другой версией, при
  первом `sync --full` сбрасывается.
* **Слаги принимают буквы любого алфавита**, а не только `[a-z0-9]`. Это
  касается точного поиска по слагу, резолва ссылок, валидаторов загрузки и
  скаффолдера. Скрипт `scripts/check-ascii-slug-class.mjs` в `verify` ловит
  новые ASCII-only проверки слагов.
* **`dream` пишет страницы на языке исходного текста** (задача #25). Метки
  концептов тоже на этом языке (ADR-0002). Английский «исходный язык» из
  upstream в форке не используется.
* **`extract_atoms` применяет те же фильтры, что и `synthesize`**
  (`dream.synthesize.min_chars`, `exclude_patterns`), задача #29.
* **Некорректный holder в takes** отклоняется до того, как заблокирует fence
  страницы.
* **Своих миграций схемы у форка нет.** Миграция Cyrillic-fold для
  `page_aliases` убрана. Существующие алиасы пересчитывает вручную
  `gbrain reindex --aliases` (на чистой базе не нужно).
* **CI форка** идёт на GitHub-hosted runners (`ubuntu-latest`), не на
  self-hosted. На сервере это не влияет.
* Версия в `VERSION` форка совпадает с upstream, на котором он основан
  (на момент написания `0.60.282.0`). Форк не имеет собственной нумерации.

## 3. Подготовка сервера

1. **Проверь ресурсы.** При 1 ГБ RAM нужен swap (1 ГБ и больше), параллельные
   воркеры Postgres выключены, `shared_buffers` порядка 128 МБ. Иначе первая
   же миграция или реиндекс уронит сервер по OOM.
2. **Postgres с расширениями `vector` и `pg_trgm`.** Минимальную версию в
   репозитории не нашёл. На реальном VPS стояли Postgres 17 и pgvector 0.8.6 из
   репозитория PGDG, бери их или новее.
   Проверь: `SELECT extname FROM pg_extension;` после `CREATE EXTENSION`.
3. **Bun 1.4.0 или новее.** `curl -fsSL https://bun.sh/install | bash`,
   затем PATH. Node ставить не нужно, gbrain работает на Bun.
4. **Отдельный Linux-пользователь `<RUN_USER>`** (вопрос 3), если gbrain
   будет отдаваться агенту. Каталог другого пользователя должен быть
   закрыт (`chmod 750` на домашний каталог), чтобы процесс агента не видел чужих файлов.
5. **Файлы с секретами** (`~/.gbrain-database-url`, ключ провайдера) создавай
   с правами `600`, владелец — `<RUN_USER>`. Временные файлы делай через `mktemp`:
   на Ubuntu 24 `protected_regular` не даёт перезаписывать чужие файлы в `/tmp`.

## 4. Установка форка

На сервере путь через `bun install -g github:…` проверяли мало. Проверенный
путь — клон и запуск из исходников.

```bash
git clone https://github.com/rustam-python/gbrain.git ~/gbrain
cd ~/gbrain
git checkout <FORK_COMMIT>
bun install
```

Запуск через обёртку (бинарь не собираем, на слабом сервере это лишняя
нагрузка). Положи в `~/.local/wrappers/gbrain` и дай `chmod +x`:

```bash
#!/bin/sh
set -a
. "$HOME/.gbrain-env"
set +a
exec bun "$HOME/gbrain/src/cli.ts" "$@"
```

`~/.gbrain-env` (права `600`) нужен каждому процессу gbrain: CLI, `serve`,
supervisor, хукам. В нём как минимум:

```bash
GBRAIN_DATABASE_URL=<DB_URL>
GBRAIN_FTS_LANGUAGE=russian        # только если заметки на русском, см. раздел 5
```

Если все же нужен глобальный пакет (`bun add -g github:rustam-python/gbrain#<FORK_COMMIT>`),
всегда указывай хэш коммита. Ветка `#master` оставляет в `bun.lock` старый коммит,
и обновление молча не происходит.

## 5. Русский язык: FTS

**Это самая частая ловушка.** Язык полнотекстового поиска хранится в индексе
`search_vector`, но берётся из переменной окружения `GBRAIN_FTS_LANGUAGE`.
Если индекс построен под `russian`, а процесс запущен без переменной, запросы
идут по `english`, и keyword-поиск расходится с индексом. На реальной базе
частое слово («по») давало таймаут keyword-поиска (около 26 тыс. чанков, 22 с).

Порядок для сервера с русскими заметками:

1. Задай `GBRAIN_FTS_LANGUAGE=russian` **постоянно и для всех процессов**:
   запиши в `~/.gbrain-env` и, если есть systemd-юниты, добавь
   `EnvironmentFile=` или `Environment=` туда же. Проверь, что её видят и `serve`,
   и supervisor.
2. На чистой базе реиндекс не нужен, но переменная должна быть задана ДО
   `gbrain init`: миграция v123 один раз прошивает язык в триггеры, и потом смена
   переменной на запись не влияет. Если язык надо сменить на уже созданной базе
   или она уже наполнена (восстановление из дампа), сначала сделай
   `pg_dump -Fc`, затем:
   ```bash
   gbrain reindex-search-vector --dry-run
   gbrain reindex-search-vector --yes
   ```
   Команда возобновляется. При падении по `statement_timeout` просто запусти
   её снова. Ориентир: 18,8 тыс. страниц и 46 тыс. чанков заняли около 10 минут.
3. Перезапусти `serve` и supervisor.
4. Проверь `gbrain doctor`: чека `fts_reindex_incomplete` быть не должно.
5. Откат: тот же `reindex-search-vector` с прежним значением переменной.

Морфология (стемминг русских форм) в форке вне охвата: цель форка в целостности
данных, а не в качестве поиска.

## 6. База и init

1. Создай роль и базу `gbrain` (согласуй с пользователем, это `CREATE DATABASE`).
2. **Миграции на роли без прав суперпользователя падают на event trigger
   (миграция v35).** На реальном сервере пришлось на время миграций выдать
   роли `SUPERUSER` и `BYPASSRLS`, после чего `SUPERUSER` отозвали, а
   `BYPASSRLS` оставили. Спроси пользователя, согласен ли он на такую
   схему, и только тогда делай:
   ```sql
   ALTER ROLE <db_role> SUPERUSER BYPASSRLS;   -- до миграций
   ALTER ROLE <db_role> NOSUPERUSER;           -- после, BYPASSRLS остаётся
   ```
   Код миграции подтверждает: `CREATE EVENT TRIGGER` доступен только
   суперпользователю. Альтернатива без выдачи прав: создать функцию
   `auto_enable_rls()` и триггер `auto_rls_on_create_table` от суперпользователя
   вручную (SQL лежит в `src/core/schema-migrations/v035-auto-rls-event-trigger.ts`),
   миграция тогда пройдёт сама. Зачем `BYPASSRLS` после миграций, в коде я не
   проверял. Спроси пользователя, оставлять ли его.
3. `gbrain init` с Postgres, не PGLite (init сам советует Postgres начиная с
   1000 файлов). Для живой проверки эмбеддингов в окружении должен быть
   `OPENROUTER_API_KEY` (рецепт `openrouter`, даже если адрес провайдера другой),
   иначе init упадёт на проверке ключа. Можно пропустить её через
   `--skip-embed-check`, но тогда проверь эмбеддинги сам в шаге 11:
   ```bash
   gbrain init --url "$GBRAIN_DATABASE_URL" --non-interactive \
     --embedding-model openrouter:<EMBED_MODEL> --embedding-dimensions <EMBED_DIMS> \
     --expansion-model openrouter:<CHAT_MODEL> --chat-model openrouter:<CHAT_MODEL> \
     --search-mode <SEARCH_MODE>
   gbrain doctor --json
   ```
   Флаги сверены с `gbrain init --help` на версии `0.60.282.0`. `init --url`
   пишет `database_url` в `config.json`. Если версия
   другая, перечитай справку. `<EMBED_DIMS>` фиксируется при создании схемы. Смена модели с другой
   размерностью потом требует реэмбеддинга всей базы.
4. Проверь версию схемы: `gbrain doctor` должен показать схему на `head`.
   Если база не новая, а восстановлена из дампа, смотри раздел 9.

## 7. Провайдер моделей

Сервер не тянет локальный инференс, модели идут через облачный
OpenAI-совместимый API (вопрос 5).

* Эмбеддинги и чат подключаются через рецепт `openrouter`, а адрес
  провайдера задаётся в `provider_base_urls.openrouter`. Так форк пользователя
  работает с российским агрегатором без отдельного рецепта.
* В id модели может быть символ `~` (например, `~deepseek/deepseek-v4-flash-latest`).
  Это часть id («актуальная версия»), не опечатка. Сохраняй его как есть.
* Реранкер на этом провайдере не работал: при проверке на VPS каталог его
  перечислял, но эндпоинт отдавал 404 (это наблюдение, в коде его не
  проверить, перепроверь на своём провайдере). Ставь `search.reranker.enabled false`, пока
  пользователь не подтвердил обратное (вопрос 8).
* Ключ провайдера положи в файл, а не в команду. В конфиг gbrain он попадает
  через переменную окружения или `config.json` с правами `600`.

Пример `~/.gbrain/config.json` (прочие ключи не трогай; `database_url` туда уже записал
`init --url`, переменную `GBRAIN_DATABASE_URL` при этом можно не задавать):

```json
{
  "engine": "postgres",
  "embedding_model": "openrouter:<EMBED_MODEL>",
  "embedding_dimensions": <EMBED_DIMS>,
  "expansion_model": "openrouter:<CHAT_MODEL>",
  "chat_model": "openrouter:<CHAT_MODEL>",
  "provider_base_urls": {
    "openrouter": "<API_BASE>"
  }
}
```

Два слоя настройки, как и в локальном runbook: файловый
`~/.gbrain/config.json` читается первым и побеждает базу. Модели
`embedding_model`, `expansion_model`, `chat_model` живут только в нём.
Остальные ключи ставит `gbrain config set` (таблица `config` в базе):

```bash
gbrain config set search.mode <SEARCH_MODE>
gbrain config set search.reranker.enabled false     # если ответ на вопрос 8 — «нет»
gbrain config set agent.use_gateway_loop true       # иначе doctor предупреждает, а агентные фазы dream не идут на не-Anthropic моделях
```

Для русских заметок добавь подсказку извлечения фактов (имя владельца в
именительном падеже) — текст и условия в `docs/agents/local-deploy.md`, раздел 5.
Если в базе уже есть своё `facts.extraction_prompt_appendix`, не затирай его.

## 8. Обновление форка

1. Перед обновлением `pg_dump -Fc` в `<BACKUP_DEST>`.
2. `git fetch` и `git checkout <новый коммит форка>` в `~/gbrain`, затем
   `bun install`.
3. Миграции применяются при первом запуске или явно:
   `gbrain apply-migrations --yes --non-interactive`.
4. `gbrain doctor`: код возврата 0, схема на `head`.
5. Перезапусти `serve` и supervisor.

Для глобального пакета: `bun remove -g gbrain`, затем
`bun add -g github:rustam-python/gbrain#<коммит>`.

## 9. Если базу восстанавливают из дампа

Дамп с другой машины вписывается в схему форка не всегда.

* Чекни версию схемы дампа и версию схемы форка. Если дамп новее форка,
  форк его не поймёт. Если старше, миграции дойдут сами.
* Старая версия форка штамповала миграцию v179 по-своему, из-за чего
  миграция upstream «индексы sync-run» могла быть пропущена. Лечится после
  апгрейда: `gbrain repair request-indexes --apply`.
* После восстановления из дампа пересчитай алиасы, если заметки на русском:
  `gbrain reindex --aliases`, и сделай `gbrain sync --full` по каждому source,
  чтобы слаги с `й`/`ё` перешли на новую грамматику (старые страницы
  превращаются в двойников и закрываются автоматически, 72 часа можно вернуть).
* Токены доступа (`bootstrap-harness`) между версиями схемы не переносятся.
  Перевыпускай командой `gbrain bootstrap harness` на запущенном
  `gbrain serve --http`.

## 10. MCP и агент на сервере (если нужно)

Только если ответ на вопрос 12 — «да».

* gbrain запускают как ленивый stdio-сервер с урезанной поверхностью:
  `gbrain serve --surface verbs` отдаёт семь команд памяти (`recall`,
  `remember`, `entity`, `synthesize`, `forget`, `context_pack`, `delta`).
  Этого хватает для телефона и бытового агента. Полный MCP не включай без
  причины.
* Инструмент `forget` и ему подобные закрой за подтверждением.
* Проверка сквозная: `remember` одного факта, затем `recall` через клиента.
  Скажи пользователю, какой факт сохранил, и предложи убрать его.
* Агент-обёртка в `~/.local/wrappers` должна идти в PATH раньше настоящего
  бинарника, иначе безопасные флаги не сработают. Обёртка должна пропускать
  подкоманды (`install`, `update`) без ограничивающих флагов.
* У агента на сервере нет собственной песочницы. Безопасность держится на
  ограничении доступа: роль базы без `DROP`/`TRUNCATE` для повседневной
  работы, полная роль только для миграций, регулярные бэкапы.

## 11. Проверка после установки

Выполняй по порядку и останавливайся на первой ошибке.

```bash
gbrain --version                      # версия форка
gbrain doctor --json                  # схема на head, нет fts_reindex_incomplete
gbrain config get search.mode
gbrain models doctor                  # пробный вызов каждой модели, около 1 токена
gbrain remember "проверка установки" --content-origin inferred   # запись
gbrain recall "проверка установки"    # чтение обратно
```

Для русских заметок добавь пару проверок:

* `GBRAIN_FTS_LANGUAGE` виден процессам `serve` и supervisor
  (`cat /proc/<pid>/environ | tr '\0' '\n' | grep FTS`).
* Страница с именем «Пётр Иванов» и страница «Петр Иванов» получают разные
  слаги, но резолвятся в одного человека через алиасы.

После проверки отзови тестовый факт: `gbrain forget <fact-id>`. Это снимает
факт с активной памяти, но текст остаётся в истории и бэкапах. Скажи об этом
пользователю и назови, что именно отозвал.

## 12. Что осталось на пользователе

Сообщи пользователю в конце, что не сделано без его решения:

* бэкапы (место и расписание, вопрос 13),
* роль базы с урезанными правами для повседневной работы,
* регистрация source с заметками и первый импорт,
* перенос данных со старой машины, если он нужен.
